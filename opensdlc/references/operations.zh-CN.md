# 工程实践

[English](operations.md) · 简体中文

涉及项目接入、自动执行、评测、发布或维护时读取。核心流程见 [SKILL.md](../SKILL.zh-CN.md)，
所有输出遵循 [文档约定](artifacts.zh-CN.md)。下文 `T` 表示 `.opensdlc/tasks/<task-id>`。
写文档前读取仓库 `.opensdlc/config.json` 和所选语言的对应模板；新任务标识遵循解析后的
语言（`zh-CN` 为简体中文，否则英文），已有任务标识不变。使用
[模板目录](artifacts.zh-CN.md#templates)中的固定落点，不另创文档。

<a id="artifacts"></a>
## 产物、确认与恢复

任务入口固定为 `T/task.md`，新会话先找原目录。每个变更应能回答“为什么做、决定做什么、
准备怎么做、实际做了什么”。小任务写在入口的对应章节，长文按文档约定拆分。
已有 Issue、PR、需求系统或设计文件是权威来源时，入口只链接正文；不要为了文件名复制内容。

在同次工作中读入最新权威记录并写回结果，互链任务与实际提交或 PR。确认引用实际决定，
不能凭空补写；后续阶段读取被接受的内容，修订改变确认基础时只重新处理受影响的决定。

跨会话的恢复信息写入 `T/task.md#handoff` 或 `T/handoff.md`。接手时核实分支、工作区、
审查、CI 和未确认的外部动作，避免重复部署或覆盖他人修改。记录保持当前可执行状态，
修订保留在 Git 或原平台，不另写逐轮对话摘要。除非要求翻译，否则保留已有文档语言。

<a id="design-detail"></a>
## 设计、实现与可观察结果

按实际影响展开 API、数据、权限、UX、兼容性和错误行为；前端可用现有设计工具迭代原型，
认可结果连同交互要求写入 `T/task.md#spec` 或 `T/spec.md` 后交给 Coding Agent，
必要本地附件存 `T/assets/`；已有设计平台只引用。不是每项任务都需要新的设计工具。
对不确定的第三方能力读实际文档或做最小隔离实验，不据猜测生成接口。

缺陷测试须能在修复前按预期失败、修复后成功。优先先提交复现测试；原测试已经复现时
直接引用其版本。确定性限制或独立 diff 审查用于保护检查有效性。
验证结果写入 `T/task.md#verification` 或 `T/verification.md`。无法复现时明确证据缺口，
继续定位，不虚构红—绿记录。需求确需改变测试时将预期变更交由适当负责人确认，
不能由作者一边改变验收标准一边宣布问题已解决。

UI 用真实运行结果而非仅看组件源码；涉及数据回退时验证数据恢复，涉及共享逻辑时检查
相邻调用方。普通文案改动不跑无关大套件，但文档写出可执行命令时要核对其真实性。产品 README、用户指南、API 与架构模板
只服务实际文档任务，不要求生成一整套文档站点。

<a id="autonomy"></a>
## 自主执行与分阶段接入

有明确、被接受的计划后，使用宿主已许可的自动执行能力处理常规编辑与测试，避免逐编辑
等待。共享指令、可运行检查、权限和审查未建立前，不扩大自主范围；不要把“auto”
等同于忽略权限。并行 worktree 也受同样约束，数量受审查与集成能力限制。

基础能力可先接入：意图归档、项目上下文、Skills、只读计划、反馈检查、动作边界。
然后连接依赖：意图＋Skills 支撑设计；项目上下文支撑并行，连同反馈检查支撑 Agent 评测；
审查读取上下文、规则与计划，并使用可靠的审查配置。审查和动作边界就绪后接流水线，
最后将观测接回意图并验证回退。无前置条件的能力可以并行建设。
接入情况写入 `.opensdlc/project.md#native`，适用但未接通的能力留下具体后续任务。

接入重复流程时采用“手动跑通 → 复用命令 → 事件触发”。事件可以是意图接受、规格接受、
PR 合并、告警或日程。读取实际被接受的产物再继续；不默认安装事件总线或编排服务。
无人值守通过原生确定性检查或独立评审决定继续、停止或转人工，不凭 Agent 自报置信度放行。

<a id="controls"></a>
## 原生控制优先

**先列真实边界，再选最少实现。** 在 `.opensdlc/operations.md#controls` 说明边界与实际
控制入口；由部署平台执行的批准和 CI 已完成的检查直接复用。需要防止 Agent 在动作发生时
越界，使用宿主 Hook、工具权限或平台权限；不能用事后 CI 冒充已经阻止了生产写入。

团队可维护的规则随仓库版本化；必须不可绕过的规则由管理员在宿主或部署平台托管。
对确需加强隔离的环境，按其数据与权限边界应用以下现成能力，而非复制企业配置全家桶：

- 限定安全命令与可用工具；禁止本地配置、参数或重试绕过托管限制。
- 使用真正的文件系统／网络隔离，同时防止 shell 读取凭据；工具层禁读不能替代进程隔离。
- 按需要限定插件来源、MCP 服务和最低受支持版本；中央分发使组织会话使用一致规则。

限制必须可测试：允许合法操作、阻止受限操作，并显示原因和批准路径。使用宿主与平台日志
保留决定，不建立第二份日志系统。强制隔离不可用时不改到隔离外执行受限动作。
具体宿主设置需查当前官方文档，不把示例版本号或平台专属字段硬编码进通用 Skill。

**三个不同概念：** 有效测试负责行为，必要授权负责权限，记录负责说明发生了什么。
文档里写“允许”、环境变量非空或发现命令含有某个单词，都不能替代真实身份和授权结果。
安全边界需由可信系统执行；不声称一个 Agent 可修改的本地脚本绝对不可绕过。语言配置只决定新正文和新任务名称，不授予权限。

<a id="eval-detail"></a>
## 评测与审查的实际落地

评测方法和数据入口写入 `.opensdlc/evals/suite.md`，具体样例及运行报告遵循文档约定。
先利用真实历史任务建立最小有区分度的 Agent 样例集，再随工作扩展；没有预算时不复制几十
条虚构案例充数。持续 CI 或明确的离线周期都必须实际运行，实质配置发布需有适用结果。
评测退化意味着需要理解并审查，不得自行降低标准、改预期或将未运行记为成功。

共享审查规则使用 `.opensdlc/review.md`，任务审查在 `T/task.md#review` 或 `T/review.md`
关联实际意见与处理结果。PR 修复和重新审查是不同动作：调用集成前读取其实际契约，
不假设某个评论命令既会审查又会修代码。自动作者只推修复，代码负责人决定是否批准；
可自动处理意见，不自动授予自己批准。
日常自测、最终新上下文验收和 PR 审查也不是同一个结果，不互相冒充。

PR 正文优先使用仓库已有模板，没有时使用双语 `pull-request.md` 模板。在原生平台更新
正文并从任务中引用，不额外保存 `pr.md`。

<a id="operations"></a>
## 发布与运行回流

复用已有模型接入、CI、运行隔离和部署工具；模型通道可由组织现有云协议提供，不强制某家
平台。通用操作写入 `.opensdlc/operations.md#delivery`，正式发布记录为
`.opensdlc/releases/<release-id>.md`，任务交付章节链接真实 PR 或发布入口。
写入先走 PR，部署接口按环境限制，生产授权与日常开发权限分开。
已有可调用受限部署接口时不再包装一个 MCP 服务；缺少权限时只能准备并报告待执行事项。

回退要在事故前演练。恢复方案考虑数据与旧版本兼容，不能只验证一个 rollback 命令存在。
执行后查询实际状态；有观察窗口就报告其已覆盖范围，没有长期观测证据就不声称长期稳定。

监测与响应说明使用 `.opensdlc/operations.md#observe`。检测规则使用有依据的阈值或滚动
基线，同时观察突变与缓慢变化。均值、标准差及分级控制带只是已有监控可采用的方案，
不要求所有指标套同一种分布或固定倍数。保留记录、诊断、受限
处置的区别，模型负责解释与建议，不负责决定原始阈值是否已经触发。

事故、工单和协作频道都进入相同处理链。小而明确的问题可以紧凑地形成 PR，但意图、方案、
验证与审查仍需可读；较大问题进入正式意图入口。团队能修正诊断假设，Agent 在原线程回复
实际恢复结果；诊断、恢复和复盘共用 `.opensdlc/incidents/<incident-id>.md`，并用事故评测
防复发。需要修复时关联任务意图及后续发布；已有事故系统保持权威正文，只在固定位置引用。

聊天中的“我会监控”不是后台服务。只有实际部署的调度、监控或受控服务能持续触发；
未接入时写明未接入和负责接续的入口，不能宣称生命周期已经自动闭环。

<a id="metrics"></a>
## 度量与改进

下表是能力改进的观察点，不是每次任务要填的验收表。优先读取 Git、工单、PR、CI、
运行日志／OpenTelemetry、监控和事故系统的既有数据；缺数据不捏造数字。
采用的指标、来源和复查安排写入 `.opensdlc/operations.md#metrics`，不另建逐任务报表。

| 能力 | 过程观察 | 结果观察 |
|---|---|---|
| 意图 | 首次提出至归档的时间 | 接受比例；设计开始后意图改动 |
| 需求与设计 | 意图至规格的耗时 | 构建开始后的规格返工 |
| 实现计划 | 首次实现即合并的比例；计划认可至合并时间 | 返工次数；最终变更与计划一致性 |
| 项目上下文 | 已有规则仍未避免的重复错误 | 新成员首次合并耗时 |
| Skills | 规则变化至 Skill 更新的延迟 | 对应规则仍被违反的审查发现 |
| 并行协作 | 质量不降时的并行数；指导与等待时间 | 合并吞吐与返工率一起看 |
| 持续反馈 | 首次 CI 成功比例 | 审查耗时与变更失败 |
| Agent 评测 | 通过表现；事故转回归样例耗时 | CI 捕获与生产遗漏的回归 |
| PR 审查 | 首次审查时间；Agent 自行解决意见的比例 | 合并前发现与上线后遗漏的缺陷／漏洞 |
| 动作边界 | 各授权点实际等待 | 越界进入生产的事件 |
| 流水线 | 无需人工介入即可完成的失败诊断比例 | 现有交付效能／DORA 指标 |
| 运行回流 | 异常至进入意图队列的时间 | 诊断变为合并修复的比例；同类事故复发 |

<a id="platform"></a>
## 平台接入资料

确需组织级配置时，依次查实际宿主的组织接入、配置优先级、托管配置、权限、沙箱、Hooks、
Skills／插件分发、受管 MCP、模型／网络部署、监控及活动审计文档。入口见
[宿主原生入口](artifacts.zh-CN.md#native)。记录本项目实际使用的位置，验证允许与受限操作，
不能只复制示例配置而跳过本环境验证。

保留宿主可执行配置的原生语法，不随文档语言变化。所有新文档按模板目录选择模板。
